# CMoSA_fail：容量格点矩保持形状适配的失败复盘

## 1. 方法概述

CMoSA（Capacity-Lattice Moment-Preserving Shape Adaptation）面向有限容量的电动汽车充电站占用预测。

给定站点容量 `C`，模型在离散支持集 `0, 1, ..., C` 上输出占用概率质量函数（PMF）。CMoSA 的核心假设是：

> 基线模型已经能够预测占用水平和总体离散程度，但概率分布仍存在可以从最近 168 小时支持窗中迁移的高阶形状误差。

CMoSA 的设计包含四个步骤：

1. 使用 Beta-Binomial 基线输出有限容量 PMF。
2. 在容量格点上构造端点、三次和四次形状方向。
3. 将形状方向投影到常数、一阶矩和二阶矩的正交补空间。
4. 使用支持窗内的预测残差驱动形状更新，使更新后的 PMF 保持：
   - 概率和为 1；
   - 预测均值不变；
   - 预测二阶矩不变；
   - 概率仍位于合法容量支持集上。

因此，CMoSA 的可证伪主张不是“增加一个更大的网络后性能提高”，而是：

> 在均值和方差保持不变的条件下，支持窗中的高阶形状残差能够迁移到未来查询，并改善概率预测质量。

## 2. 最终失败结论

在修正实验职责隔离后，CMoSA 没有显示出相对于基线的改善，因此创新主张停止。

协议正确的最小正式验证使用：

- B：只使用 source-fit 训练 Beta-Binomial backbone；
- A：冻结 B 后，只使用 source-meta 情节训练 CMoSA 形状头；
- validation：14 个站点、224 个情节、1344 个有效查询；
- 预测跨度：未来 1–6 小时。

结果：

| 方法 | site-macro dCRPS |
|---|---:|
| B：Beta-Binomial 基线 | 1.490581 |
| A：CMoSA | 1.490656 |
| A − B | +0.0000753 |

差值在 1–6 小时全部为正，表示 CMoSA 在该协议下均略差于基线。

结论是：

> 当前证据不支持“支持窗高阶形状残差能够在保持低阶矩的同时带来可迁移概率增益”这一主张。

此前曾观察到 A 优于 B 的结果，但这些结果使用了混合 source-fit 和 source-meta 情节的训练协议。混合职责违反了原定实验契约，因此全部作废，不能用于证明创新有效。

## 3. 失败原因

### 3.1 训练职责混用导致早期正结果失效

最重要的问题是 backbone 训练数据没有严格限制为 source-fit。早期运行把 source-fit 和 source-meta 情节混在了基线训练中，而 CMoSA 形状头也使用 source-meta。

这造成了两个问题：

1. backbone 可能间接使用了本应只用于形状头训练的情节；
2. A 和 B 的信息职责不再符合预先定义的训练协议。

在这个错误协议下，A 相对 B 出现了小幅改善。但修正为：

```text
B backbone 只使用 source-fit
A shape head 只使用 source-meta
```

后，A 不再改善，反而在所有预测跨度上略差。

这说明早期正结果主要反映了实验协议污染，而不是可靠的创新增益。

### 3.2 先观察到小范围正信号，再发现协议错误

最初的非训练 pilot 和混合职责训练都显示出微小改善。问题在于，正信号出现后没有立即执行完整的信息职责审计，而是继续实现和扩展对照实验。

正确顺序应该是：

1. 先验证训练数据角色是否完全符合方案；
2. 再检查每个模型是否访问了相同的信息范围；
3. 最后才解释性能差异。

如果先把结果当成创新信号，再回头检查协议，容易把数据泄漏、样本组成差异或实现差异误认为方法收益。

### 3.3 形状残差的可迁移性没有被基线独立证实

CMoSA 假设“低阶矩已经正确，高阶形状仍有可预测误差”。但在正式验证之前，没有先用独立诊断确认：

- 基线均值误差是否已经足够小；
- 基线方差误差是否已经被充分控制；
- 支持窗形状残差是否跨情节稳定；
- 残差是否比随机噪声更能预测未来查询。

因此，CMoSA 直接把一个尚未确认的统计现象作为中心机制。最终结果显示，在严格协议下，这种形状增量没有表现出稳定收益。

### 3.4 复杂机制没有超过简单基线

CMoSA 引入了：

- 支持窗伪预测；
- 残差统计；
- 容量相关投影；
- 非负概率更新；
- 矩保持约束；
- 小型形状头。

这些步骤增加了实现和计算复杂度，但正式验证没有获得可重复增益。对于这种结果，不能继续增加网络容量、训练轮数或附加模块来“挽救”主张，因为那会改变问题并掩盖核心假设未成立这一事实。

### 3.5 M 灵活分布对照曾出现数值不稳定

两成分 Beta-Binomial 对照 M 的第一版实现出现了 NaN 和训练坍塌，原因包括：

- PMF 为不同容量样本使用了 padding；
- 无效容量格点在 `lgamma` 计算中先产生非法数值；
- 混合两个带 `-inf` 的 log-PMF 时产生了不稳定梯度；
- 训练过程缺少及时的有限值断言。

之后改为：

1. 先在合法容量支持上计算概率；
2. 混合两个合法 PMF；
3. 显式归一化；
4. 最后再转换为 log-PMF。

M 才恢复为可运行状态。但 M 在小规模 validation 上的 dCRPS 为 `2.861089`，明显差于 B 和 A，因此没有解释 CMoSA 的失败或早期正信号。

### 3.6 对照实验的实现曾出现非独立问题

U 和 G 的第一版代码实际上使用了相同的零残差输入，因此两者并不是独立对照。这个问题在结果产生后才被发现，随后才修正为：

- U：保留支持残差，但不施加矩保持约束；
- G：去除支持残差，仅保留其他输入。

这说明对照实验不能只依赖命令参数区分，必须在运行前检查实际张量、参数和数据流。

## 4. 工程和实现层面的暴露问题

### 4.1 pandas 列名与方法名冲突

`data.mask` 被 pandas 解释为 DataFrame 方法，而不是名为 `mask` 的列，导致情节构造和契约验证第一次运行失败。

防错方式：

```python
data["mask"]
```

对于可能与 DataFrame 方法同名的列，始终使用显式列索引。

### 4.2 站点采样不均衡

最初的情节选择器在达到总情节数后停止，导致“16 个站点”的评分实际只来自 1 个站点。

防错方式：

- 先固定站点数量；
- 再为每个站点分配近似相同的情节配额；
- 报告实际站点数、情节数和查询数；
- 站点宏平均不能在只有一个站点时被误认为跨站点结果。

### 4.3 PMF padding 和容量支持没有从一开始统一处理

不同站点容量不同，批处理需要使用 `C_max` padding。若无效格点参与 `lgamma`、softmax、混合或 CRPS 计算，就会出现：

- NaN；
- 错误归一化；
- 无效类别梯度；
- 伪造的极端概率。

防错方式：

1. 在所有概率运算前建立合法支持 mask；
2. 无效格点使用安全参数计算或完全排除；
3. 概率混合后在合法支持上重新归一化；
4. 每个 batch 断言概率和、非负性和有限值；
5. 对容量 `C≤2` 显式回退，因为此时矩约束已经确定分布。

### 4.4 训练脚本没有默认保存完整协议

早期训练结果虽然保存了 seed 和损失，但没有足够强制地记录：

- source-fit/source-meta 角色；
- 训练池和验证池；
- 情节数和站点数；
- anchor checkpoint 哈希；
- 处理版本；
- 评分协议。

防错方式：训练脚本启动时必须输出并保存完整实验契约；缺少关键字段时直接拒绝运行。

### 4.5 数值错误没有在最小运行中立即失败

A 形状头第一次训练曾经以 NaN loss 结束，但脚本仍输出 `TRAIN_COMPLETED`。这会把失败 checkpoint 伪装成可用模型。

防错方式：

- loss 非有限时立即抛出错误；
- 梯度非有限时立即抛出错误；
- checkpoint 只有在所有 epoch 和有限值检查通过后才能保存；
- 结果状态区分 `COMPLETED`、`FAILED_NUMERIC` 和 `BLOCKED`。

## 5. 哪些部分是有效的

失败不等于所有工作都无效。以下部分经过验证并可以复用：

1. 精确 `HH:55` 目标定义；
2. 缺失目标保留为 mask，不进行标签插补；
3. 168 小时支持窗和 1–6 小时预测跨度；
4. 精确坐标组隔离；
5. source / validation / calibration / test 的职责划分框架；
6. 有限容量 PMF 的支持约束；
7. 离散 CRPS 评分；
8. CMoSA 投影算子的概率和、均值和二阶矩数学检查；
9. B/A/U/G/M 的统一评分接口设计。

这些工程和评价资产可以服务于新的创新假设，但不能被解释为 CMoSA 已经有效。

## 6. 以后设计创新时必须遵守的流程

### 阶段一：先证实问题存在

在提出新模块前，先回答：

- 基线主要错误来自均值、方差还是分布形状？
- 错误是否在支持窗和未来查询之间稳定迁移？
- 简单校准或后处理能否解释全部收益？
- 该现象是否在多个站点和多个时间块重复出现？

只有当问题诊断成立，才进入机制设计。

### 阶段二：冻结数据职责

为每个数据池写出明确角色：

```text
source-fit      训练共享 backbone
source-meta     训练适配器或形状头
validation      选择配置
calibration     独立校准
test            最终一次性评价
stress          预先定义的压力评价
```

每个模型都要记录自己能访问的池、时间段、标签和统计量。任何角色不一致，结果不得进入比较表。

### 阶段三：先实现最小可证伪版本

新方法至少需要同时实现：

- 强基线；
- 同参数量的简单控制；
- 去除中心信息源的控制；
- 灵活分布族控制；
- 统一评分器。

新方法只有在这些控制下仍然保持优势，才值得扩大训练规模。

### 阶段四：先做协议审计，再解释结果

每次运行后先检查：

1. 训练数据角色；
2. 站点数和情节数；
3. 时间边界；
4. 目标 mask；
5. 容量支持；
6. 预测和标签对齐；
7. PMF 有限性和归一化；
8. checkpoint 与配置绑定。

协议审计通过后，才讨论性能差异。

### 阶段五：设置明确停止条件

以下任一条件成立时，应停止扩展：

- 修正协议后新方法不再优于基线；
- 收益只能在混用数据职责时出现；
- 简单控制解释全部收益；
- 灵活分布族表现更好且更简单；
- 数值实现无法稳定复现；
- 改变 seed 后收益方向不一致。

停止实验不是失败管理不足，而是防止把无效假设包装成方法贡献。

## 7. 最终经验

CMoSA 失败的核心不是“模型太小”或“训练轮数不够”，而是中心统计假设没有在正确的数据职责协议下得到支持。早期正结果由协议混用造成，修正后收益消失。

最重要的经验是：

> 先验证数据和协议，再验证机制；先验证机制，再扩大实验；任何协议修正都必须使此前结果重新分级，而不是继续沿用有利结果。
